# 场景动态构建与增强可视化的先后关系

更新日期：2026-10-27。本文确定论文与平台后续开发的目标流程。这里的“动态构建”指智能体根据任务选择已有场景资源，并由平台沿真实 YK 中线完成定位、加载和多模型装配；不包括由智能体生成新的构件几何。

## 目标流程

1. **任务理解与装配规划**：智能体识别展示目标、目标里程和所需资源；平台校验任务结构、资源依赖、同屏兼容性和数据来源。
2. **场景动态构建**：平台加载并定位资源，按需保留或切换前一阶段资源，形成最终的三维场景。此阶段只使用模型本身必需的基础显示状态，不执行针对任务的高亮、透明、剖切、标签或视角优化。
3. **构建结果校验与冻结**：确认目标 YK 里程、实际加载资源、空间变换、场景对象状态及资产版本；保存可追溯的构建结果。任一必需模型失败时，任务停在构建失败状态，不进入增强阶段。
4. **构建后增强决策与执行**：智能体依据任务目标和已校验的最终场景，决定关注对象及增强策略；平台校验策略适用性、冲突和性能约束后，应用显隐、透明、剖切、标签、标准视角等效果。增强计划必须引用对应的构建结果，而不是在装配前假定对象已存在。
5. **效果验证**：分别评价场景构建是否正确，以及增强后是否更容易辨认任务重点、遮挡是否减少、画面和交互是否可用。增强失败应撤销已施加的视觉改动，并明确报告；已验证的构建结果可保留，不能把增强失败误报为装配失败。

多阶段装配时，第 2 步可以逐阶段推进，但第 4 步须等待最终场景通过第 3 步校验。资源固有的颜色、纹理或必要可见性属于基础展示，不计为论文所研究的“构建后增强”。

## 当前实现与待改造处

当前 `SceneExplorationWorkflow` 在每个 `scene.show-resource` 步骤调用 `withScenePlan`。它的实际顺序是“资源加载 → 立即生成并应用该阶段增强计划 → 业务动作”，下一阶段又会撤销旧增强并重新应用。因此目前具备资源装配和增强引擎，但**尚未实现上述先完成整体构建、再进行任务驱动增强的两阶段流程**。`assemble_scene_at_mileage` 默认传入 `auto` 增强方式；数据库中的步骤完成也不能单独证明“构建后增强”已实现。

改造时应先把场景任务的最终装配结果作为独立状态和快照，再开放基于该快照的增强决策、规则校验和执行入口。构建、增强各自记录状态、耗时、失败原因与效果指标；质量检查等其他工作流可继续沿用现有事务机制，不必为论文场景流程改写全部平台能力。
