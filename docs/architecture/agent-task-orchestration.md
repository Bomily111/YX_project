# 智能体任务编排接入

日期：2026-10-12

## 2026-10-19 自主调度原型

论文所说的“调度”是智能体按任务目标调用平台能力进行场景构建与可视化，不依赖尚未接入的装备调度版块。对话中的表单直接调用共享控制器创建任务；自然语言场景请求由模型选择 `SCENE_EXPLORATION_RESOURCES` 中的资源及顺序。两条入口先经过 `TaskContext`、`WorkflowPlan`、`ScenePlan` 的现有结构与业务规则校验。自然语言入口现先调用 `prepare_platform_task`，再由模型根据每步返回状态调用 `advance_platform_task`；后者检查任务 ID 和当前步骤，只推进一步。失败、任务被替换或无进展时停止，不盲目重试。表单仍可由确定性调度器连续推进，作为人工对照。

围岩资源已增加 `rock.geophysical-grade`、`rock.tsp-hardness`、`rock.tsp-integrity` 和 `rock.tem-resistivity`。它们复用现有 ShareVolume 图层，加载时等待体素真正就绪，任务步骤可按目标选择。物探层源锚点为 YK2+244；在数据不足的演示阶段，可依据工地 YK 中线位置和方向把体素矩阵示意重定位到任务里程。TSP 原始报告里程为 X1DK2+937，演示位置不能被叙述成目标工点实测。单例体素渲染器当前采用阶段切换，不能同屏叠加这四层。

2026-10-19 的真实页面回归中，本地 Qwen 2.5 7B 选择 `rock.geophysical-grade → rock.tem-resistivity`。它先生成并校验两步计划，再分别调用 `advance_platform_task`；第二次调用使用第一步反馈中的 `currentStepId`，平台状态达到 `2/2 completed`。一次早期回归暴露工具 Schema 用 `stepId`、模型却回传 `currentStepId` 的不一致，已统一字段并增加回归测试。中途模型只回复文字时，对话循环会向模型补充一次未完成状态，并把后续工具集缩为状态查询和下一步执行；平台仍不替模型自动推进。围岩 JSON/体素纹理已纳入构建时 SHA-256 资产清单，用于新生成的任务快照。

本地 Qwen 2.5 7B 曾在明确要求执行时选择旧的 `compose_scene_workflow`，只生成计划。对话层现在按用户本轮明确意图将这一调用路由至受控调度器，保留模型选出的资源顺序；“只生成计划、等待确认”仍停在计划边界。审计同时记录模型原选工具、平台实际执行工具、资源序列与逐步结果，便于分辨模型策略和确定性护栏的贡献。最终执行消息取平台状态与调度轨迹，避免模型把内存增量估算说成实际消耗等无依据结论。

`backend` 的 `agent:export-trajectories` 命令把合格的智能体调度审计导出为本地 JSONL，包含目标、模型选择、意图路由和平台反馈。它是后续训练/评估的数据入口；当前还没有监督微调、强化学习、标准任务集或跨模型效果结论。

## 接入原则

智能体和表单不各自维护任务状态。`TaskWorkflowPanel` 仍负责可视化确认与人工操作，但通过 `TaskWorkflowBridge` 注册唯一活动控制器；智能体工具调用同一控制器，因此两种入口共享同一个 `TaskContext`、`WorkflowPlan`、`WorkflowExecutor`、`ScenePlanExecutor` 和 `EnhancementEngine`。

智能体不能直接修改 Cesium 对象，也不能绕过任务校验。资源加载、视觉增强、业务动作和回滚仍由现有确定性执行链完成。

## 第一版平台工具

| 工具 | 当前行为 |
|---|---|
| `create_task` | 接收描述、隧洞、起止里程和内存预算，生成并校验 TaskContext；第一版同时生成确定性的初始 WorkflowPlan 与 ScenePlan |
| `create_workflow` | 读取已校验的步骤、依赖和资源计划，不执行业务步骤 |
| `execute_task_step` | 事务式执行当前步骤 |
| `continue_workflow` | 从当前步骤连续执行至完成或失败 |
| `get_task_status` | 只读返回任务 ID、状态、进度、步骤、资源计划和共享上下文字段 |
| `retry_task_step` | 清理并重试失败步骤 |
| `reset_task_scene` | 逆序撤销业务与增强副作用，释放任务资源并保留应用级资源 |

所有工具返回 JSON 文本，至少包含 `ok`、`action`、任务状态、当前步骤、进度、步骤列表、上下文字段和场景计划。面板未挂载或操作不满足状态约束时，由工具注册中心返回明确错误，不伪造成功结果。

## 当前主场景入口（2026-10-21）

普通“在某里程构建/展示/装配场景”请求只向模型暴露 `assemble_scene_at_mileage`。模型只需提交资源 ID 和目标里程；工具从用户原话复核唯一里程、用中线数据确定镜头位置、校验每个资产的覆盖范围与同屏兼容性，并在平台内部完成工作流执行。返回实际活动根资源；失败时保留明确原因。显式要求逐步修订的试验仍可使用原准备、推进、修订工具。

首页采用右侧完整对话栏，装配成功后左侧和底部呈现真实目标里程、已加载资源和任务状态摘要。完整任务面板改为按需打开的“任务运行记录”，工具调用不再自动弹出它。左/底摘要目前只显示可由执行结果核实的二维状态信息，尚未接入围岩或支护业务图表。

## DeepSeek 与提示词验证（2026-10-22）

平台保留已有的 TypeScript 浏览器 Agent 循环和确定性任务执行链。后端通过 DeepSeek 的 OpenAI 兼容接口接入，密钥只放在被 Git 忽略的 `backend/.env`。默认模型为 `deepseek-flash`，普通工具调用采用非思考模式；接入更复杂的长时任务前，再评估 LangGraph 的持久状态、暂停恢复和人工介入能力。框架选择不改变平台负责结构、规则校验和真实场景执行的边界。

系统提示词以“识别意图→提取唯一目标 YK 里程→选择最少相关资源→单次调用装配入口→依据返回事实说明结果”为主线。资源映射覆盖设计分级、物探融合分级、TSP 坚硬度/完整度、TEM 视电阻率和结构树支护；示例资产允许按目标中线示意重定位，但回答必须区分源工点与展示位置。质量检查、只规划、显式分阶段试验保留独立路径。

提示词质量先用在线任务集衡量，而不只检查文字：至少覆盖明确目标与多资源选择、缺少里程时澄清、互斥解释层逐层展示、只规划不执行、平台拒绝后不编造成功。记录期望工具及参数、模型实际工具及参数、平台校验结果、最终话术和错误类型；后续修改提示词应在同一任务集上重跑。当前在线回归已覆盖“坚硬度＋支护组合”选资源、缺里程澄清、TEM 视电阻率映射和只规划不执行；尚未据此宣称场景已在浏览器中完成 DeepSeek 实装配。

## LangChain 接入（2026-10-22）

DeepSeek 已改由后端 LangChain 的 `ChatOpenAI` 兼容客户端接入。`ChatPromptTemplate` 组合现有系统提示词与对话历史，`bindTools` 接收平台工具的 JSON Schema；模型产生的工具调用转换为现有 SSE 事件，浏览器执行平台工具后以关联的 `tool_call_id` 把结果送回模型。DeepSeek 采用非思考模式以适配当前工具结果往返链。其他提供方暂沿用原适配器。

LangChain 当前负责模型调用、提示词编排与工具调用生成；浏览器端 Agent 循环负责工具调用与结果的往返，因为 Cesium Viewer 和资源控制器驻留浏览器。`TaskWorkflowBridge`、任务规则校验、资源加载、回滚与三维执行仍是平台的确定性职责，不能仅依赖提示词或 LangChain 工具 Schema 来保证。在线回归已通过模型选资源和 `/api/ai-agent/chat` 两轮工具调用/结果反馈；完整浏览器三维装配还需单独验收。

若一次模型响应包含多个工具调用，浏览器现在将它们保留在同一条 assistant 消息中，再依次追加对应的工具结果，避免下一轮模型对话中的调用 ID 与消息结构失配。

普通同屏场景请求只向模型提供 `assemble_scene_at_mileage`。同一轮即使模型生成多个装配调用，平台也只执行第一个，并为后续调用返回明确拒绝结果；明确要求逐层、分阶段或先后展示时仍使用阶段任务工具。这样工具选择与实际执行次数都受到代码约束，而不是只依靠提示词。

## 界面联动（早期原型）

早期版本的 AI 助手通过“任务”入口和自动 `task:open` 事件展开任务确认面板。当前普通场景装配已收敛为单一工具，运行记录只在用户点击入口时打开；底层校验、审计、快照和复位能力仍保留。

系统提示词要求：跨模块分析或里程支护质量检查优先使用 `create_task` 和 `create_workflow`；生成计划后默认等待用户要求再执行，除非用户明确要求直接完成；模型不得编造场景或增强结果。

## Agent 循环修正

每轮工具执行结果现在以标准工具消息写回 Agent 对话历史，保留工具调用 ID、工具名、输入和结果，下一轮模型可基于真实结构化状态决定继续、查询或停止。工具内部 JSON 不直接显示在聊天气泡中，界面只呈现工具状态和模型整理后的自然语言答复。

后端的 OpenAI Compatible、Claude 与 Ollama 适配器均会转换这份统一消息格式，并尊重请求级模型覆盖。Ollama 流式响应中的 `message.tool_calls` 会被标准化成前端统一消费的 SSE 工具事件，因此本机 Qwen 与外部兼容服务共用同一套前端 Agent 循环。

SSE 读取采用跨数据块缓冲，后端流式错误会转成明确异常，不会因 JSON 被拆包而静默丢失工具调用。

## 里程参数确定性归一化

模型可能把 `DK278+330` 的偏移量误填为 `330`。`create_task` 在业务工具边界重新解析任务描述中的完整桩号，并以 `278330`、`278340` 覆盖不可靠的模型参数；系统提示和工具 Schema 同时说明转换规则。该防线不依赖具体模型是否理解桩号格式。

## 浏览器验证

真实页面已验证以下流程：

1. 打开 AI 助手并点击标题栏“任务”。
2. 任务面板显示与原独立入口相同的表单。
3. 生成质量检查任务，得到 2 个工作流步骤与 2 份场景资源计划。
4. 执行围岩步骤，进度变为 `1/2`，共享上下文写入 `rock.grade`、`rock.anomalies` 和 `rock.confidence`。
5. 复位后进度恢复 `0/2`，增强计划与指令归零，围岩和支护任务资源均为 `idle / 0`，仅公共隧道保持 `loaded / 1`。

连接实际后端后又验证了自然语言闭环：用户输入“请创建一个检查 DK278+330 至 DK278+340 初期支护质量的任务，先生成计划并等待我确认”，Ollama/Qwen 发出真实 `create_task` 工具调用；共享任务面板自动展开，起止里程为 `278330` / `278340`，生成 2 个步骤和 2 份场景计划，状态为“待执行”、进度 `0/2`。模型随后读取工具结果并用自然语言提示用户确认，未自动执行步骤。

## 后续拆分

第一版优先打通自然语言入口与现有可靠执行链。下一步再将 `get_step_result`、`query_resources`、`apply_scene_plan` 和 `apply_enhancement_plan` 暴露为细粒度、可审计工具，并为每次工具调用记录输入参数、耗时、结果和回滚状态。

## 2026-10-23 自主装配验收边界

DeepSeek 经 LangChain 选择单一装配工具后，真实浏览器已完成设计围岩分级、物探融合分级、TSP 坚硬度及完整度、TEM 视电阻率，并完成 TSP 坚硬度与结构树支护组合的同屏任务。左侧资源摘要与目标 YK 里程、PostgreSQL 任务终态及实际资源/资产版本一致。模型决策集 9 个案例连续 3 轮为 27/27；这是任务理解和工具参数基线，不代表像素级可视化质量。单独结构树钢架在数据库完成且仅加载所选 GLB，但无头软件 WebGL 页面未通过响应时限。详细证据和浏览器环境限制见 [回归记录](../verification/2026-10-23/agent-browser-regression.md)。

## 2026-10-27 研究流程确认

论文场景任务明确采用“**先动态构建并校验完整场景，后根据任务增强该场景，再分别验证构建与增强效果**”的顺序。模型在构建阶段选择已有资源，平台负责真实装配；增强阶段须以最终构建结果为输入，而不是在每个资源刚加载时立即作最终增强决策。当前 `withScenePlan` 的逐阶段增强属于已有平台机制，尚不等同于目标研究流程。状态边界、失败处理和改造入口见[构建后增强架构约定](post-assembly-enhancement.md)。

施工任务交互不应要求用户说出 TSP、TEM 或资源 ID。当前“某里程展示某模型”的句子是资源级连通性测试；论文评价改用“初期支护施工交底需要查看岩体坚硬程度与既有支护布置”等任务语言，观察智能体是否从工程信息需求选择资源，并在目标与数据类型含糊时追问。任务语言的在线选择与真实页面回归见[施工任务语言验证](../verification/2026-10-27/construction-task-language.md)。
