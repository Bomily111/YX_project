# 任务工作流模型（第一版）

更新日期：2026-10-11

## 职责边界

- `TaskContext` 只描述任务本身，不保存页面或 Cesium 对象。
- `TaskTemplate` 把三类标准任务转换为确定性的步骤序列。
- `WorkflowPlanner` 负责选择模板；任务校验失败时不生成计划。
- `WorkflowValidator` 负责验证系统模板或智能体生成的计划，不执行场景操作。
- `WorkflowContext` 只允许步骤写入自身声明的 `outputKeys`，并为每个值保存来源步骤、记录时间和可选置信度。
- `WorkflowExecutor` 通过动作处理器执行步骤；处理器不直接改变流程状态，只返回结构化输出并登记副作用回滚函数。

## 当前硬约束

1. 步骤 ID、输入、输出和依赖均不得重复。
2. 依赖必须存在并位于当前步骤之前，依赖图不得形成环。
3. 非任务输入必须来自当前步骤的直接或间接前置步骤，不能依赖无关分支的偶然执行顺序。
4. 一个输出字段只能由一个步骤负责，避免后续步骤读取到含义不确定的覆盖值。
5. 步骤声明的能力必须由目标模块提供。
6. 模块只能读取步骤声明的输入，并只能写入步骤声明的输出。

## 标准模板

| 任务类型 | 当前流程 |
|---|---|
| 施工组织 | 围岩状态识别 → 爆破参数复核 → 人员设备组织 |
| 质量检查 | 围岩等级与异常评估 → 初期支护适配性检查 |
| 风险处置 | 通风异常分析 → 人员设备处置方案 |

模板用于建立稳定基线，后续智能体生成的自定义计划仍须通过同一个 `WorkflowValidator`，不能直接操作 Viewer 或绕过模块能力检查。

## 执行与回滚

执行器一次只运行一个步骤。步骤开始前读取其声明输入并确认所有依赖已经完成；动作成功后先检查完成条件，再原子写入共享上下文。未声明输出或缺少必需输出均视为失败。

动作一旦产生模型、事件监听或图表等副作用，应立即通过 `onRollback` 登记清理函数。这样即使动作在返回结果前抛错，执行器也能清理已产生的副作用。后续步骤失败时，默认按照已完成步骤的逆序执行回滚、删除其上下文输出并恢复为待处理状态；修复问题后重试会从最早被回滚的依赖重新执行。

需要场景资源的业务动作通过 `withScenePlan` 包装。包装器负责在动作前选择并加载资源，并把步骤执行前的活动 `ScenePlan` 纳入同一个回滚函数，因此业务处理器只需负责查询、分析及自身产生的临时对象。

手动跳过一个步骤会级联跳过所有依赖它的后续步骤，防止后续步骤在缺少输入的情况下继续运行。`reset()` 会逆序撤销所有完成步骤，并把计划恢复到初始待处理状态。
